## 0. 공통 원칙

- **MVP 흐름과 공존하지 않고 바꾼다.** 출시 기준 티켓은 새 표시값(예: `deliveryMode = "curatedV2"`, 또는 `flow = "launchV1"`)을 달고, 앱은 지금처럼 모르는 방식의 티켓을 "이전 방식 촬영"으로 안내한다(지금 `isCurated` 처리와 같은 방식). MVP 교차 조합·현장 실증이 끝난 뒤 단계별로 바꾼다.
- **지금 구조를 그대로 쓴다.**
  - 순수 규칙은 `SBSNCore`에 두고 단위 시험한다(예: 공개 위치 계산, 수락 시한, 편집 기간, 연락처 탐지, 촬영 길이).
  - Firestore 접근은 `SBSNBackend`의 `nonisolated static` + `AsyncThrowingStream` 리스너 패턴(`FirestoreListeners`)을 따른다.
  - 두 앱이 같이 쓰는 화면은 `SBSNUI`(지금 `TicketChatView`·`ParticipantsMapView`)에 둔다.
  - 쓰기는 서버 커밋 뒤 화면을 바꾼다(`CustomerTicketView`의 `ticketBeforeWrite` 방식).
  - 시한(5분 수락, 24시간 잠금, 7일)은 **서버 시각 기준**이다. 앱은 표시만 하고, 판정은 규칙·함수가 한다.
- **초 단위 카운트는 쓰지 않는다**(D051). 남은 시간은 분 단위 또는 "14:10까지" 같은 시각으로 보인다.
- **교차 조합**: 상태 이름·문구·시험 식별자(`accessibilityIdentifier`)를 Android와 맞춘다. 단계마다 iOS ↔ Android 네 조합으로 한 사이클을 본다.
- **예시 화면 정리**: 실제 화면이 된 예시(`CustomerFeatures`·`PhotographerFeatures`의 작가 프로필·활동 위치·휴게·수락 설정·바구니·계정 연결·전문 보정 등)는 그 단계에서 예시 목록에서 뺀다(D036 때 P6·P8과 같은 방식).

## 1단계 — 계정과 지도

### 1.1 로그인·계정 연결(두 앱)

- 방향(L04 확정): **고객은 로그인 없이(익명) 지도·프로필을 보고**, 채팅·신청 전에 Google·Apple 로그인한다. 지금 익명 계정에 **연결**(`link`)해 uid를 유지한다. **작가 앱은 처음부터 로그인**한다.
  - 상대에게 보이는 이름은 앱 닉네임이다(L06). 처음 로그인할 때 기본 닉네임을 자동으로 만들고 마이에서 바꾼다. 계정 실명·이메일은 상대·보정사에게 보이지 않는다. 그래서 Apple이 첫 로그인 때만 주는 이름은 화면에 쓰지 않는다(M2, 서버 프로필에 남길지는 웹과 맞춘다).
  - 가입할 때 만 14세 이상 확인 한 줄을 둔다(L28 자리, 문구는 정책 세션).
  - MVP 익명 계정·데이터는 출시 계정으로 옮기지 않는다(L05).
  - 근거: 심사 지침 5.1.1(v) "계정 기능이 핵심이 아니면 로그인 없이 쓰게 하라", 4.8 "Google 로그인을 넣으면 같은 조건의 다른 로그인(Apple 로그인)도 넣어라"(2026-10-16판).
- 화면(공용 `SBSNUI.SignInSheet`)

```
┌──────────────────────────────┐
│  십분스냅에 로그인             │
│  채팅과 촬영 신청은 로그인 뒤   │
│  할 수 있습니다.                │
│                              │
│  [  Apple로 계속하기      ]   │  ← 위에 둔다(같은 크기)
│  [ G  Google로 계속하기   ]   │
│                              │
│  [✓] 만 14세 이상입니다         │  ← L28 자리
│  계속하면 이용약관·개인정보     │
│  처리방침에 동의합니다 ▸        │  ← 동의 방식은 정책 세션 안
```

- 연결 흐름
  1. 익명 사용자에 Apple·Google 자격 증명을 `link`한다. 성공하면 uid가 같아 티켓·찜·구매·presence가 그대로다.
  2. **이미 다른 계정에 연결된 자격 증명**(`credentialAlreadyInUse` 17025)이면: 그 계정으로 로그인(`signIn`)하고 익명 계정은 버린다. 익명으로는 둘러보기만 하므로(신청·채팅 전 로그인, L04) 옮길 데이터가 없다(B1-2 단순화).
  3. 로그인 계정이 바뀌면(uid 변경) 세션이 리스너·FCM 토큰 등록·로컬 활성 티켓을 새 uid로 다시 시작한다. 지금 `CustomerSession.reissueAccount()`(디버그 "익명 계정 재발급")와 같은 경로를 정식화한다.
- 계정 삭제(마이 → 계정 → 계정 삭제, 두 앱). **삭제를 막지 않는다**(L10).

```
┌──────────────────────────────┐
│ ‹ 계정 삭제                    │
│ 삭제하면 되돌릴 수 없습니다.     │
│ ⚠ 진행 중인 촬영 1건은 취소되고   │  ← 있을 때만. 환불은 취소·환불 규칙대로

│ • (작가) 정산할 금액이 있으면     │
│   지급한 뒤 삭제가 끝납니다       │
```

  - Apple 로그인 사용자는 다시 Apple 로그인으로 authorization code를 받아 `Auth.revokeToken(withAuthorizationCode:)` 뒤 삭제한다(Firebase가 Apple 토큰을 저장하지 않음).
  - 서버 데이터 삭제·익명화는 호출형 함수 하나로 한다(B1-3). 앱은 함수 성공 뒤 로그아웃하고 로컬(활성 티켓 ID, 작가 앱 티켓 폴더, 캐시)을 지운다.
- 바뀌는 파일
  - `SBSNBackend/Backend.swift`: `SignIn` actor → 계정 서비스(익명 시작, `link`, `signIn(with:)`, 로그아웃, 삭제, 로그인 상태 스트림). 동시 로그인 한 번만 하는 지금 보호는 유지
  - 새 `SBSNBackend/AccountService.swift`(Apple nonce·Google 자격 증명 만들기, 오류 코드 → 안내 문구)
  - 새 `SBSNUI/SignInSheet.swift`, `SBSNUI/AccountDeletionView.swift`
  - `sbsn/CustomerSession.swift`, `sbsnPhotographer/PhotographerSession.swift`: uid 변경 처리, 로그인 필요 시점 게이트
  - 작가 앱 첫 화면: 로그인 → 역할 문서 확인 → 승인 전이면 "작가 승인 대기" 화면(L07, 촬영 가능 켜기 막음). 같은 계정으로 고객 앱도 쓴다
  - 작가 기기 하나(L08): 다른 기기에서 촬영 가능을 켜면 이 기기는 꺼지고 "다른 기기에서 촬영 가능을 켜 이 기기는 꺼졌습니다"를 보인다(presence의 발행 기기 값으로 판단)
  - 시험 로그인(L09): 디버그 빌드 + sbsn-dev에서만 이메일·비밀번호 시험 계정 화면을 연다
  - `sbsn/ContentView.swift`(로그인 실패 화면), `sbsn/Tabs/CustomerMyTab.swift`·`sbsnPhotographer/Tabs/PhotographerTabs.swift`(계정 섹션, 예시 "계정 연결" 제거)
  - 두 앱 entitlements(Sign in with Apple), Info.plist URL Types(`REVERSED_CLIENT_ID`), `GoogleService-Info.plist` 다시 받기(커밋하지 않음), 패키지 `GoogleSignIn` 10.1.0 이상(Firebase 13과 맞는 판)
- 재사용: 지금 `SignIn` actor의 "진행 중인 로그인 함께 기다리기", 디버그 "익명 계정 재발급"(시험용으로 남김)
- 위험
  - **같은 Apple·Google 계정이면 두 앱의 uid가 같다**(Firebase Auth uid는 프로젝트 단위). 작가가 고객 앱도 쓰면 같은 uid가 `customers/{uid}`와 `photographerPresence/{uid}`를 함께 갖는다. 자기 자신 매칭은 규칙(`customerUid != photographerUid`)이 막는다. 역할은 운영 승인 역할 문서로 정한다(L07, B1-4).
  - 작가 기기는 하나다(L08). 앞 기기의 위치 세션·리스너를 확실히 멈춰야 공개 위치가 두 곳에서 튀지 않는다(B1-5).
  - Apple: 2026-01-01부터 한국 개발자는 Services ID를 새로 등록·수정할 때 서버 간 알림 엔드포인트(이메일 전달 변경·계정 삭제 알림)를 넣어야 한다. Firebase 설정에 Services ID가 필요하므로 엔드포인트가 먼저 있어야 한다(B1-6).
  - 익명 계정 30일 자동 삭제(Identity Platform)를 켜면 둘러보기만 한 사람의 기록이 지워진다. 연결된 계정은 지우지 않는다.
- 백엔드에 필요한 것: B1-1~B1-6("백엔드에 필요한 것" 표)

| 약관 | Google 지도를 다른 지도와 함께·가까이 쓰지 않는다, 지도 콘텐츠 사전 저장·스크래핑 금지, 로고·저작권 표시를 가리지 않는다, 앱 약관에 Google 지도 사용과 Google 약관·개인정보처리방침 적용을 적는다 | MapKit을 한 화면에 섞지 않는다(전환은 한 번에), 하단 카드가 로고를 가리지 않게 지도 padding을 준다, 지도 스냅숏을 저장하지 않는다, 약관 문구는 정책 세션에 요청 |
| 묶음 | SDK 자체 묶음 기능은 문서에서 못 찾음. `google-maps-ios-utils` 7.1.2가 SPM·SDK 11 지원(SDK 10~12 미만) | **두 플랫폼 공통 200m 격자 규칙으로 앱이 직접 묶는다(L30, M3)**. 유틸은 쓰지 않는다(SDK 12 의존 문제도 없어진다) |

- MapKit 대비 위험
  - 지금 쓰는 SwiftUI `Map`(선택 `tag`, `UserAnnotation`, `MapCameraPosition.automatic`)을 모두 직접 구현해야 한다. 접근성(VoiceOver 마커 이름)과 UI 시험 식별자도 래퍼가 맞춰야 한다. 지금 드라이버는 `marker.<이름>` 식별자로 마커를 누른다.
  - 키 남용 요금은 회사 책임이다. 무료 SKU라도 결제 계정에 예산 알림을 둔다.
  - Android는 이미 Google Maps라 같은 지도 위에서 교차 조합 화면을 비교하기 쉬워진다.
- 되돌리기: 래퍼 뒤에 지도 구현을 숨기면(입력 = 핀 목록·카메라, 출력 = 선택·보이는 범위) MapKit으로 돌아가기 쉽다.

### 1.3 지도 화면(고객): 화면 범위 작가 표시, 축소 시 숫자 묶음

```
┌──────────────────────────────┐
│ (지도 | 목록)          [필터] │  ← 목록·필터는 지금 예시 자리
│                              │
│      ●김작가          ③       │  ← 200m 칸 안 무작위 점(1분 갱신)
│            ●박작가            │     ③ = 축소했을 때 묶음
│   ☕이작가(휴게 · 점심 13:00까지)│  ← 휴게 중 표시(신청 불가, 채팅 가능)
│        ◉ 나                   │
│                    [⌖ 내 위치] │
│ ┌──────────────────────────┐ │
│ │ 김작가 · 촬영 가능           │ │  ← 핀을 누르면 하단 카드
│ │ 추천 20분 · 평균 2시간 안 전달 │ │
│ │ 10분 9,000원 · 5분당 3,000원  │ │  ← 이 작가가 정한 가격(D057)
│ │ 사진 장당 6,000원             │ │
│ │ [프로필 ▸]   [채팅하기]      │ │
│ └──────────────────────────┘ │
│ Google                        │  ← 로고는 가리지 않는다
└──────────────────────────────┘
```

- 화면 범위 조회: 지도를 움직여 멈추면(`idleAt`) 보이는 범위로 다시 조회한다. 서버가 주는 범위 조회 방식(칸 ID 목록 또는 지오해시 범위, B1-7)에 맞춘다. 한 번에 최대 100명(지금 규칙의 `limit`과 같은 방식).
- 묶음(L30): 두 플랫폼 공통 규칙이다. 200m 격자 칸을 확대 수준에 따라 2배씩 합친 큰 칸으로 모아, 한 칸에 둘 이상이면 숫자 원으로 보인다. 원을 누르면 그 칸으로 확대한다. `SBSNCore` 순수 함수와 Android `:core`가 같은 시험 벡터를 쓴다.
- **공개 위치(L02 확정)**: 작가 앱이 **기기에서** 200m 칸 번호와 칸 안 무작위 점을 계산하고, 서버에는 칸 번호와 표시점만 보낸다. 정밀 좌표는 매칭 전 서버로 가지 않는다(지금 100m 격자도 기기에서 뭉갠다).
  - 무작위 점은 (작가·칸·공개 세션)마다 고정한다. 같은 칸에 있는 동안 1분마다 다시 보내도 점은 같다. 칸을 옮기거나 촬영 가능을 새로 켜면(새 공개 세션) 새 점을 뽑는다.
  - 계산: 공개 세션 비밀값(켤 때 기기에서 만든 난수) + 칸 번호로 결정적 난수를 만들어 칸 안 좌표를 고른다. 비밀값은 서버에 보내지 않는다. 규칙은 `SBSNCore`에 두고 Android와 같은 시험 벡터로 맞춘다.
  - 서버 규칙은 표시점이 그 칸 안에 있는지만 검사할 수 있다(정밀 좌표는 모른다).
- 반경(L11): 반경 밖 고객에게도 핀은 보이되 카드에 "활동 범위 밖"을 보이고 [촬영 신청]을 막는다(채팅은 가능). 반경 값은 300m·500m·1km·2km.
  - **D065로 정해졌다**: 고객 앱이 자기 위치에서 작가 200m 칸까지 최단 거리로 판정하고, 고객 위치는 서버에 보내지 않는다. 화면과 위치를 모를 때의 처리는 2.2(결정 S2).
- 휴게·제재(L12): 휴게 중이면 핀에 사유와 끝 시각("휴게 · 점심 13:00까지")을 보이고 신청은 막고 채팅은 열어 둔다. 제재 제한 중인 작가는 지도에서 숨긴다(서버가 조회에서 뺀다).
- 바뀌는 파일
  - `sbsn/Map/PhotographerMapView.swift`: `Map` → `GoogleMapView`, 범위 조회·묶음, 하단 카드(프로필·채팅하기). 지금 "이 작가와 촬영하기"(즉시 확정)는 2단계에서 채팅·신청으로 바뀐다
  - `SBSNBackend/PhotographerDirectory.swift`: 범위 조회 리스너, 공개 위치 필드
  - `SBSNCore/Presence.swift`: `publicGridMeters` 100 → 200, 칸 번호·칸 안 고정 무작위 점(L02), 상태(휴게), 반경·종료 시각, 묶음 함수, 반경 판정
  - `sbsnPhotographer/PhotographerLocationTracker.swift`·`PhotographerSession.swift`: 공개 위치 발행 방식(B1-8에 따름)
- 재사용: `GeoPoint.quantized`(칸 계산), `PhotographerPresence.isSelectable`(잠김·오래됨 거르기), 지금 heartbeat 3분·25m 이동 규칙(1분 갱신 요구에 맞춰 조정)

## 2단계 — 매칭·채팅·작가 상태·촬영 길이(설계 v1)

- 작성 `sbsn_ios`, 2026-11-23. 기준은 D063·D064·D065와 웹 계약 `firebase/docs/launch-phase-2.md`(ac8a13f)·공통 벡터(b4978fa)다. 0단계 설계안(위 1.3의 반경 줄, 아래 B2 줄)보다 이 절이 앞선다.
- **2단계에는 결제가 없다**(D064). 신청 함수의 입력은 방 ID·촬영 시간·재시도 식별자뿐이다(계약 1). 그래서 신청 화면에는 촬영 시간만 고르고, 사진·보정 장수와 금액, `[결제 자리]`는 4단계에 붙인다(→ 결정 S4).
- 2단계가 끝나면 출시 방식으로 매칭 → 채팅 → 위치 → 시작 → 촬영 중 연장 → 종료까지 돈다. 종료 뒤 사진 전달은 3단계 갤러리 v2가 같은 `ticketId`로 잇는다. 그 사이 sbsn-dev에서는 종료 뒤가 비어 있다(D063 ③).
- 이 단계에서 지우는 MVP: 고객 확정 트랜잭션(`TicketService.confirm`)·`customers/{uid}` 잠금, presence `activeTicketId`로 매칭을 아는 작가 경로, MVP 만남 화면(`CustomerTicketView`·`PhotographerTicketView`의 매칭·시작 부분), MVP 채팅 알림 경로, 예시 `requestPolicy`·`breakTime`·`activityArea`·`photographerProfile`과 "고객이 확정하면 바로 매칭됩니다" 문구들. MVP 갤러리·사진 전달은 3단계에서 바꾼다.

### 2.0 상태와 빠져나오기(두 앱 공통)

```
 신청 대기(5분) ──수락──▸ 시작 대기 ──둘 다 시작──▸ 촬영 중 ──누구든 종료──▸ 종료
   │                        │                        (자동 종료 없음, L21)
   ├ 고객 신청 취소           ├ 고객 일방 취소(사유)
   ├ 작가 거절               └ 작가 일방 취소(사유)
```

### 2.1 탭과 대화 목록

- 대화방이 작가(고객)마다 하나라 대화 목록이 필요하다. 두 앱 모두 **채팅 탭을 더한다**(→ 결정 S1).
  - 고객: 촬영 · **채팅** · 내 사진 · 마이 / 작가: 촬영 · **채팅** · 내역 · 마이
  - 줄마다 상대 닉네임, 마지막 메시지 한 줄(사진이면 "사진"), 시각, 안 읽은 수, 상태 꼬리표(`신청 대기 14:10까지`·`시작 대기`·`촬영 중`).
  - 목록은 본인 참여 조건과 페이지 크기(20)로 읽는다(계약 데이터 표).
- 익명 고객은 채팅 탭에 "로그인하면 작가와 대화할 수 있습니다 [로그인]"만 보인다(L04).

### 2.2 고객: 지도 카드 → 프로필 → 대화 → 신청

```
┌──────────────────────────────┐
│  (지도: 1단계 그대로, 묶음 ③)   │
│      ●김작가    ◌박작가(흐리게)  │  ← 범위 밖 작가는 핀을 흐리게
│   ☕이작가                     │  ← 휴게 중
│ ┌──────────────────────────┐ │
│ │ 김작가 · 촬영 가능 · 18:00까지│ │  map.card
│ │ 추천 20분                  │ │
│ │ [프로필 ▸]      [채팅하기]  │ │  map.card.profile / map.card.chat
│ └──────────────────────────┘ │
└──────────────────────────────┘
```

- 카드의 상태 줄(`map.card.status`)
  - 촬영 가능: "촬영 가능 · 18:00까지"
  - 휴게: "휴게 중 · 식사"(사유만, 끝 시각 없음. 계약의 `breakReason` 네 가지: 식사·이동 중·장비 정비·잠시 휴식)
  - **활동 범위 밖**(D065): "활동 범위 밖 · 이 작가는 지금 1km 안에서 촬영해요"(→ 결정 S2)
  - 제재 중인 작가는 지도에 오지 않는다(서버가 뺀다).
- **반경 판정**(D065, 웹 격자 문서 "고객 앱의 활동 반경 판정"): 고객 앱이 자기 위치를 EPSG:5179 mm로 투영하고, 작가 `cellId`의 닫힌 200m 사각형까지 최단 거리 제곱을 `radiusMeters`의 제곱과 비교한다(`PublicLocationGrid.Cell.isWithin`, 49afdac에서 공통 벡터 5건 통과). 고객 위치는 서버로 보내지 않는다.
  - 고객 위치가 바뀌거나 지도 응답이 새로 오면 다시 판정한다.
  - **고객 위치 권한이 없거나 위치를 아직 모르면** 판정할 수 없다. 신청을 막고 "내 위치를 켜면 신청할 수 있어요 [위치 켜기]"를 보인다(→ 결정 S2). 채팅은 열어 둔다.
- 프로필(`photographerProfile` 예시를 대체): 사진·닉네임·상태 줄·추천 촬영 시간·소개·[채팅하기]. 평균 전달 시간은 3단계 집계가 생기면 붙인다. 가격 줄은 4단계(S4).
- [채팅하기]: 익명이면 로그인 시트를 띄우고(L04), 로그인 뒤 `openLaunchConversationV1`로 방을 열어 대화방으로 간다.

```
┌──────────────────────────────┐
│ ‹ 김작가 · 촬영 가능      […] │  ← …: 신고·차단
│ 메시지는 마지막 촬영(또는 대화)   │  ← 보존 안내 한 줄(L18)
│ 뒤 30일 동안 보관됩니다          │
│ ─── 11/18 20분 촬영 · 종료 ─── │  ← 지난 티켓 구분선
│ 고객: 지금 경복궁인데 가능할까요? │
│               작가: 네 가능해요  │
│ ┌──────────────────────────┐ │
│ │ 촬영 시간 [－] 20분 [＋]     │ │  request.minus / request.duration / request.plus
│ │ 10~60분, 5분 단위           │ │
│ │ 작가가 5분 안에 수락하면     │ │
│ │ 매칭돼요                    │ │
│ │        [촬영 신청]          │ │  request.submit
│ └──────────────────────────┘ │
│ [＋][메시지 입력…]     [보내기] │  chat.photo / chat.input / chat.send
└──────────────────────────────┘
```

- 신청 막대는 접어 둘 수 있고(처음엔 접힘, "촬영 신청" 한 줄), 기본값은 작가의 추천 촬영 시간이다.
- 신청을 막는 경우는 단추 대신 이유 한 줄(`request.blocked`)을 보인다.
  - 휴게 중: "작가가 쉬는 중이라 지금은 신청할 수 없어요. 채팅은 할 수 있어요."
  - 활동 범위 밖·위치 모름: 위 카드 문구와 같다.
  - 다른 작가에게 신청 대기 중이거나 촬영이 진행 중: "진행 중인 신청이 있어요 [보기 ▸]"(L15)
  - 작가가 촬영 가능을 껐거나 이미 다른 촬영 중: "지금은 촬영을 받지 않아요"
- 신청 뒤: 방 위에 "20분 촬영 신청 · 14:10까지 수락 대기 [신청 취소]"(`request.cancel`). 취소는 확인 한 번("신청을 취소할까요?")이고 사유를 묻지 않는다(제재 집계 밖).
- 결과는 서버가 넣는 시스템 메시지로 방에 남는다: 수락 "매칭됐어요. 만날 곳을 정해 주세요", 거절 "작가가 이번 신청을 받지 않았어요", 자동 거절 "작가가 다른 촬영을 수락했어요", 만료 "작가가 5분 안에 답하지 않아 신청이 취소됐어요".
- 수락되면 촬영 탭이 티켓 화면(2.5)으로 바뀌고 대화방 위에도 [🗺 위치]·[시작 대기] 막대가 생긴다.

### 2.3 작가: 촬영 가능(반경·끝 시각)·휴게·새 신청

촬영 탭(홈)

```
┌──────────────────────────────┐
│ 촬영 가능 · 1km · 18:00까지      │  home.status
│ [변경]   [휴게]   [끄기]        │  availability.change / break.start / availability.off
│ ⚠ 최근 7일 응답 없이 만료 2회:   │  sanction.warning
│   한 번 더 놓치면 30분 동안 새    │
│   신청을 받지 못해요             │
│ 새 신청(2)                      │
│ ┌──────────────────────────┐ │
│ │ 고객1 · 20분 · 14:10까지     │ │  request.card
│ │ "경복궁 정문 근처예요"        │ │  ← 마지막 메시지
│ │ [대화 보기]  [거절]  [수락]   │ │  request.open / request.decline / request.accept
│ └──────────────────────────┘ │
│ (1단계 위치 안내 문구 그대로)     │
└──────────────────────────────┘
```

- 촬영 가능 켜기 시트(지금 토글을 바꾼다)

```
┌──────────────────────────────┐
│ 촬영 가능 켜기                  │
│ 이동할 수 있는 거리              │
│ ( )300m ( )500m (•)1km ( )2km  │  availability.radius.300 … .2000
│ 언제까지                        │
│ ( )1시간 (•)2시간 ( )4시간 [시각]│  availability.until
│ 고객 지도에는 200m 칸 안 임의     │
│ 지점으로 보여요                  │
│ [취소]              [켜기]      │  availability.on
└──────────────────────────────┘
```

  - 기본값은 지난번 값(처음은 1km·2시간). 끝 시각이 지나면 서버가 지도에서 빼고 앱은 발행을 멈춘다. 30분 전에 로컬 알림 "18:00에 촬영 가능이 꺼져요 [연장]"을 띄운다.
  - [변경]은 같은 시트로 반경·끝 시각만 바꾼다(새 공개 세션을 만들지 않는다). 켜기·끄기·기기 교체는 1단계 그대로(L08, 격자 문서 "활성 기기 ID").
- 휴게: [휴게] → 사유 넷 중 하나(식사·이동 중·장비 정비·잠시 휴식, `break.reason.meal` 등) → 지도에 "휴게 중 · 식사". 채팅은 받고 새 신청은 서버가 닫는다(L12). 끝 시각은 없고 [휴게 끝내기](`break.end`)로 돌아온다. 휴게 중에 들어와 있던 신청은 그대로 수락·거절할 수 있다.
- 새 신청 카드
  - 만료가 가까운 순서. 마감은 "14:10까지"만 보이고, 1분 안으로 남으면 "곧 만료"로 바꾼다.
  - [수락]은 확인 없이 바로 보낸다(5분 안이라 단계를 줄인다). 서버가 만료·세대를 따로 판정하므로 늦으면 "이미 만료된 신청이에요" 또는 "다른 신청을 이미 수락했어요"를 보인다.
  - [거절]은 확인 한 번("이번 신청을 거절할까요? 거절은 제재에 세지 않아요")이고 사유는 묻지 않는다(→ 결정 S3).
  - 하나를 수락하면 나머지 카드는 서버의 자동 거절로 사라진다(제재 집계 밖, L15).
- 제재(L16·L17): 2회째 경고 배너. 제한 중이면 "15:02까지 새 신청 제한 · 고객 지도에서 숨겨져요. 확정된 촬영과 채팅은 그대로예요"(`sanction.limited`)와 [검토 요청 ▸](`sanction.review`: 메모 한 칸 → 보내기 → "검토 중 · 영업일 3일 안에 답드려요").
- 알림을 누르면 그 신청이 있는 대화방으로 간다(신청 카드가 방 위에 고정).

### 2.4 대화방 공통(두 앱 `SBSNUI.ChatRoomView`)

- 송신은 서버 함수로 한다(계약 "채팅·첨부·알림": 같은 배포에서 클라이언트 직접 쓰기를 닫는다). 서버 커밋 뒤 말풍선을 "보냄"으로 바꾸고, 실패하면 말풍선에 [다시 보내기].
- 연락처·링크(L03): 보내기 전에 `SBSNCore.ContactFilter`가 전화번호·이메일·URL·메신저 아이디 모양을 찾으면 시트 "연락처나 링크가 들어 있어요. 운영정책상 보낼 수 없어요"와 가린 미리보기, [고치기] [가리고 보내기]. 시험 문장 목록은 Android와 같게(E15 결과에 따라 범위를 다시 본다).
- 사진(L19): [＋] → 사진 1장 → 긴 변 1,280px, 메타데이터 모두 제거, JPEG 0.8 → 서버가 정한 참여자 전용 임시 경로에 올리고, 처리기가 검사한 뒤 메시지에 붙인다. 처리 중에는 말풍선에 "사진 확인 중".
- 시스템 메시지(서버만 씀): 신청·수락·거절·만료·시작·종료·취소(사유 분류만)·연장.
- […] 메뉴: 신고(사유 고르기 + 메모), 차단(확인 뒤 이 방에 새 신청·메시지를 막음). 지금 예시 시트(`sampleChatSafetySheets`)를 실제로 바꾼다.
- 위치 단추(🗺)는 시작 대기 동안만 보인다(정밀 위치는 매칭~시작, 10초, L13·L14). 위치 화면은 1.4 그대로.

### 2.5 티켓 화면: 시작 대기 → 촬영 중 → 종료(두 앱)

시작 대기

```
┌──────────────────────────────┐
│ ‹ 김작가 · 시작 대기   [🗺][…] │  ← …: 촬영 취소(사유), 신고·차단
│ 20분 촬영 · 14:12 매칭          │
│ (대화방 그대로)                 │
│ [메시지 입력…]          [보내기] │
│ ──────────────────────────── │
│ 고객이 시작을 눌렀어요           │  ← 상대가 먼저 눌렀을 때만
│        [촬영 시작]             │  ticket.start
└──────────────────────────────┘
```

- [촬영 시작] 확인: "만나서 촬영 안내를 마쳤나요? 둘 다 시작을 누르면 20분 촬영이 시작돼요." 먼저 누른 쪽은 "상대가 시작을 누르면 촬영이 시작돼요"를 보고, 상대에게 `shoot_start_requested` 알림이 간다.
- 취소는 […] 안(`ticket.cancel`, 잘못 누르지 않게 하단에서 뺐다). 사유 시트(L17, `cancel.reason.<코드>`)

```
┌──────────────────────────────┐
│ 촬영을 취소할까요?              │
│ ( ) 일정이 바뀌었어요            │  schedule_changed
│ ( ) 상대와 연락이 안 돼요         │  no_contact
│ ( ) 상대가 약속 장소에 오지 않았어요│  no_show
│ ( ) 만나기로 한 곳에 갈 수 없어요  │  cannot_meet
│ ( ) 서로 이야기해서 취소해요      │  mutual
│ ( ) 기타 [메모…]                │  other(메모는 상대에게 안 보임)
│ [돌아가기]        [촬영 취소]    │  cancel.confirm
└──────────────────────────────┘
```

  - 취소는 바로 효력이 생긴다(상대 동의 불필요). 상대에게는 분류만 보인다("작가가 촬영을 취소했어요 · 일정이 바뀌었어요").
  - `mutual`을 고르면 상대 방에 "서로 취소에 동의하나요? [동의] [동의하지 않음]"(`cancel.mutual.agree`·`.disagree`) 카드가 24시간 뜬다. 동의하면 상호, 아니면 일방으로 기록된다(L17). 다른 사유를 고른 취소에는 카드가 없다.

촬영 중

```
┌──────────────────────────────┐
│ 김작가와 촬영 중         […]   │
│        12분 남음               │  ticket.remaining(분 단위, 1분 미만 "곧 끝나요")
│   ▓▓▓▓▓▓▓▓░░░░░░  20분 촬영     │
│   (5분 연장됨 · 14:42까지)      │
│ [5분 연장 신청] 남은 연장 25분   │  ticket.extend(고객만)
│ [💬 채팅]          [촬영 종료]  │  chat.open / ticket.end(두 앱)
└──────────────────────────────┘
```

- **촬영 종료는 두 앱 모두에 있다**(계약 "빠져나오기": 누구든 혼자 끝냄, 서버가 `endedAt`·`endedByRole` 기록). 확인 창
  - 고객: "촬영을 끝낼까요? 끝내면 다시 시작할 수 없어요. 사진은 작가가 고른 뒤 갤러리에 올라와요."
  - 작가: "촬영을 끝낼까요? 끝내면 다시 시작할 수 없어요. 끝난 뒤 사진을 골라 올려 주세요."
  - 4단계에서 확인 창에 더할 줄(지금은 넣지 않음): 고객 "지금 끝내면 남은 시간은 환불되지 않습니다", 작가 "지금 끝내면 남은 시간만큼 고객에게 환불됩니다"(L42).
  - 동시에 눌러도 서버가 첫 기록을 돌려준다. 앱은 요청 뒤 서버 기록을 읽어 "고객이 끝냈어요"/"작가가 끝냈어요"를 보인다.
- 예정 시간이 지나도 끝나지 않는다(L21). 작가 폰만 진동하고 두 앱에 "예정 시간이 지났어요"를 보인다.
- 연장(L20·L21·L45): 고객 [5분 연장 신청] → 작가 화면 위 카드 "고객이 5분 연장을 원해요 [동의] [거절]"(`extension.accept`·`.decline`, 60초 안). 동의하면 바로 늘어난다(2단계는 결제 없이 동의 뒤 적용, 4단계에 `[결제 자리]`와 철회 불가 한 줄). 거절·만료면 고객에게 "작가가 연장을 받지 않았어요". 합계 30분이면 단추를 숨긴다.
- 종료 뒤: 고객은 "촬영이 끝났어요. 사진은 작가가 고른 뒤 올라와요"(3단계 갤러리 자리), 작가는 내역에 "사진 올리기"(3단계 자리)로 간다.

### 2.6 계정 삭제가 막힐 때(D065, 두 앱)

- 서버 오류 `failed-precondition` + `details.reason = ACTIVE_SHOOTING`, `blockerKind`(`request`·`ticket`), `blockerId`를 받으면 계정 칸에 보인다.

```
│ 진행 중인 촬영을 끝내거나 취소한 뒤 │  my.deleteAccount.error
│ 삭제할 수 있습니다                 │
│ [진행 중인 촬영 보기]              │  my.deleteAccount.blocker
```

- [진행 중인 촬영 보기]
  - `ticket` → 그 티켓 화면(촬영 탭).
  - `request` → 그 신청이 있는 대화방. 신청 문서(`launchMatchRequests/{id}`, 참여자 읽기)의 방 ID로 연다. 고객은 [신청 취소], 작가는 [거절]이 바로 보인다.
- 앱이 이미 진행 중인 건을 알면 서버를 부르기 전에 같은 안내를 먼저 보인다(Apple 연결 계정이 재인증부터 하지 않게). 서버 판정이 정본이라 모르는 건은 서버 오류로 같은 화면이 된다.
- 만료된 신청은 막지 않는다(서버가 판정). 여러 건이면 서버가 티켓 → 가장 먼저 만료되는 신청 순으로 하나를 준다.

### 2.7 알림(10종, 계약 표)

- 알림 글은 서버가 넣는다(데이터에는 메시지 본문·좌표 없음). 아래는 앱이 제안하는 글이다(→ 결정 S5). 시각은 한국 시각 "14:10".

| `event` | 받는 쪽 | 제목 / 본문 | 누르면 |
| --- | --- | --- | --- |
| `match_requested` | 작가(시간 민감) | 새 촬영 신청 / 고객1 · 20분 · 14:10까지 수락할 수 있어요 | 대화방(신청 카드) |
| `match_accepted` | 고객 | 작가가 신청을 수락했어요 / 만날 곳을 채팅으로 정해 주세요 | 티켓 |
| `match_declined` | 고객 | `declined` 작가가 이번 신청을 받지 않았어요 · `auto_declined` 작가가 다른 촬영을 수락했어요 | 대화방 |
| `match_expired` | 고객·작가 | 고객: 작가가 5분 안에 답하지 않아 신청이 취소됐어요 · 작가: 답하지 않은 신청이 만료됐어요 | 대화방 |
| `match_cancelled` | 작가 | 고객이 신청을 취소했어요 | 대화방 |
| `shoot_start_requested` | 상대 | 고객1님이 촬영 시작을 눌렀어요 / 만났으면 시작을 눌러 주세요 | 티켓 |
| `shoot_ended` | 상대 | 고객1님이 촬영을 끝냈어요 | 티켓 |
| `shoot_cancelled` | 상대 | 고객1님이 촬영을 취소했어요 / 일정이 바뀌었어요 | 대화방 |
| `extension_requested` | 작가(시간 민감) | 고객이 5분 연장을 원해요 / 1분 안에 동의해 주세요 | 티켓(연장 카드) |
| `chat_message` | 상대 | 고객1 / 새 메시지가 왔어요(사진이면 "사진을 보냈어요") | 대화방 |

- `eventId`로 같은 알림을 두 번 보이지 않는다. 앱이 그 화면을 열고 있으면 배너를 띄우지 않는다(채팅). 화면에 들어오면 서버 상태를 다시 읽는다.
- 고객 앱도 출시 계정으로 알림 토큰을 등록한다(지금 고객 앱의 등록 경로를 출시 사용자 문서로 옮김, 웹과 맞출 것 W1).

## 3단계 — 갤러리 v2(D052·D053 (2))

규칙(D053 (2) 총괄 기본안, D054 L22·L23): 최소 10장 첫 공개 = "첫 업로드", 촬영 종료 뒤 24시간 안(약속, 못 지키면 촬영료 일부 환불은 4단계). 3시간 안 공개는 목표로만 보인다. 공개 목록은 최대 30장, 편집 기간에도 10장 아래로 줄일 수 없다. 공개 뒤 24시간 잠금 → 공개 7일째까지 추가·삭제·순서 변경. 구매 기한은 공개 뒤 7일 하나. 구매된 사진은 삭제 불가, 찜한 사진을 지우면 고객에게 알림. 추가 알림은 하루 1번으로 묶음. 서버 사진은 만든 뒤 30일 보관.

### 3.2 고객: 미리보기 전체·개별 저장, 상세 좌우 넘기기, 찜 일괄 구매

- 갤러리

```
┌──────────────────────────────┐
│ ‹ 김작가 · 11/22         […]  │  ← … : 미리보기 전체 저장
│ 사진 13장 · 구매 기한 11/29 14:30│
│ 포함 사진 3장 중 1장 남음 ·      │  ← 미리 산 장수와 기한(D056 자리,
│ 11/29 14:30까지 고르기           │     환불 문구는 정책 세션)
│ 새 사진 1장이 추가됐습니다       │  ← 추가 알림(하루 1번 묶음)
│ ┌──┬──┬──┐                   │
│ │♥ │  │💰│                   │
│ ├──┼──┼──┤                   │
│ │  │♥ │  │                   │
│ └──┴──┴──┘                   │
│ ┌──────────────────────────┐ │
│ │ 찜 3장  [찜한 사진 받기]     │ │  ← 포함 1장 + 추가 2장(IAP)
│ └──────────────────────────┘ │
└──────────────────────────────┘
```

- 상세(좌우 넘기기)

```
┌──────────────────────────────┐
│ ‹ 3 / 13                [⤓]  │  ← ⤓ : 이 미리보기 저장(워터마크)
│                              │
│   ‹    [  미리보기  ]    ›    │  ← 좌우로 넘김
│                              │
│ ♥ 찜     [이 사진 받기(포함)]    │  ← 포함 몫이 없으면 [추가 구매 ₩7,000]
│                                │     (작가 가격+1,000원을 스토어가 준 가격으로, 구매됨이면 "저장됨")
└──────────────────────────────┘
```

  - 미리보기 저장은 워터마크 저화질본이고 메타데이터가 없다(지금 미리보기 그대로, 워터마크 강도 유지 L24). 전체 저장은 갤러리 `…` 메뉴에 둔다(L24). 사진 앱 "추가" 권한을 처음 저장할 때 묻는다(지금 구매 저장과 같은 권한). 워터마크 미리보기는 구매 전 "시험 사용"으로 본다(L27).
  - **사진 받기 순서(D055·D056·L35)**: 미리 산 포함 장수가 남아 있으면 [이 사진 받기(포함)]로 고르고, 고른 장수를 [고르기 확정]으로 확정한다(결제 없음, 계약 이행). [고르기 확정] 옆에 철회 불가 한 줄(EC-03)을 둔다. 다 쓰면 단추가 [추가 구매]로 바뀌고 StoreKit IAP로 산다. 서버가 이 티켓의 추가 사진 가격(작가 가격 + 1,000원, D057)에 맞는 상품 ID를 알려 주고, 앱은 그 상품을 조회해 **결제 전에 스토어가 돌려준 실제 가격**(`Product.displayPrice`)을 보인다. 서버 가격과 스토어 가격이 다르면 구매를 막고 알린다(B4-5). 앱 안에 가격 비교·웹 결제 안내는 없다.
  - 포함 장수 표시: "포함 사진 n장 중 m장 남음 · 기한"을 갤러리 위에 둔다. 공개 뒤 7일 안에 다 고르지 않은 몫은 환불된다(D056, 문구는 정책 세션).
  - 미리 산 보정이 있으면 사진을 고를 때 "보정도 맡기기(포함 1장 남음)"를 함께 고른다. 고르면 보정 주문이 들어간다(5단계 흐름).
  - 찜 한꺼번에 받기(L43, Android와 같음): 앱 안 확인 한 번("찜 5장: 포함 2장 + 추가 3장") → 포함 몫부터 확정 → 추가 장수만큼 StoreKit 결제 시트를 **한 장에 한 거래씩 차례로** 띄운다. 각 결제 전에 서버가 그 사진을 예약한다(B4-4). StoreKit 수량 구매는 쓰지 않는다. 중간에 결제 시트를 닫으면 남은 장수는 멈추고 "추가 2장을 받지 않았습니다 [이어서 받기]"를 보인다. 일부 실패(기한 지남·삭제됨)는 장별로 알린다.
  - 추가 구매 버튼 옆에 철회 불가 한 줄(L35, EC-03), 구매 시트 앞에 미성년자 취소권 고지 한 줄 자리(L28). 확인 창은 따로 늘리지 않는다.
  - 작가가 찜한 사진을 지우면 그 칸이 사라지고 "찜한 사진 1장을 작가가 지웠습니다" 안내.

## 5단계 — 전문보정 주문(고객)

D051 (8): 기본 사진을 산 고객이 별도 주문, 결과 JPG, 기본본 v1·보정본 v2 따로 보관, 납기 예시 7일, 무료 수정 1회, 추가 수정은 회당 기본 보정료의 20%. 진행은 접수 → 작업 중 → 검수 → 완료, 완료 알림.

- 가격·결제(D055·D056·D057, L25를 대신함): 촬영 신청 때 미리 산 보정은 장당 최소 6,000원(PG, 패키지에 포함), 촬영 뒤 따로 주문하는 보정은 장당 최소 7,000원(StoreKit IAP). 보정 가격은 회사가 정하고 출시는 최소 금액 그대로다(L38). 신청 때 보정은 0·1장 중 고른다(L33). 1인·2인 같은 가격. 미리 산 보정은 사진을 고를 때 함께 맡기면 주문된다(3.2). 앱은 두 가격을 비교해 보여 주지 않는다.
- 들어가는 곳: 구매한 사진 상세의 [전문보정 주문], 내 사진 탭 "전문보정" 목록(예시 `retouch` 대체).

  - 완료되면 알림, **v2도 사진 앱에 자동 저장**한다(L25). v1은 지금 구매 저장본 그대로.
  - 메타데이터(L25): 보정사에게는 GPS를 지운 파일이 가고, 완성본(v2)에는 서버가 원래 메타데이터를 다시 붙인다. 앱은 받은 v2를 그대로 저장한다(앱에서 메타데이터를 고치지 않음).

- 위험

  - 작가 앱에 보정 주문을 보일지(작가 품질 피드백)는 이번 범위 밖으로 둔다.

## 결제 흐름(D055·D056)

PG 결제창·StoreKit 구매 시트의 세부는 4단계에서 설계한다. 그 전 단계에서는 아래 자리에 지금 `PaymentPlaceholderSheet`("결제 없이 계속")를 두고 기록만 한다. 결제 버튼 옆에는 철회 불가 한 줄(L27, 상품별 문구는 정책 세션), 결제 화면 앞에는 미성년자 취소권 고지 한 줄(L28) 자리를 둔다. 결제마다 확인 창을 늘리지 않는다(L27). 앱 안에 가격 비교 문구와 웹 결제 안내·링크는 넣지 않는다.

| 자리 | 결제 | 가격 | 화면 |
| --- | --- | --- | --- |
| 촬영 신청(패키지) | PG | 작가 가격(D057): 기본 10분(최소 8,000원) + 5분 추가당(최소 3,000원) × 추가 길이 + 사진 장당(5,000~20,000원) × N(1·3·5장) + 보정 6,000원 × M(0·1장)을 **하나의 가격**으로. 신청 순간 가격표 고정(L44) | 2.1 신청 막대 |
| 5분 연장 | PG | 고정된 작가의 5분 추가당 가격. 결제 버튼 옆 철회 불가 한 줄(L35 정정) | 2.5 (작가 동의 뒤) |
| 포함 사진 고르기 | 결제 없음(계약 이행) | — | 3.2 [이 사진 받기(포함)] |
| 추가 사진 | StoreKit IAP | 고정된 작가 사진 가격 + 1,000원(서버 계산, 6,000~21,000원). 스토어가 준 실제 가격을 표시 | 3.2 [추가 구매] |
| 찜 한꺼번에 받기 | 포함 몫 + 넘는 장수 IAP | 장마다 거래 하나, 결제 시트를 차례로(L43) | 3.2 |
| 미리 산 보정 사용 | 결제 없음 | — | 3.2 사진 고를 때 / 5단계 |
| 촬영 뒤 보정 주문 | StoreKit IAP | 7,000원(회사가 정함, L38) | 5단계 |
| 추가 수정 | StoreKit IAP | 보정 가격의 20%를 천 원 단위로 올림(출시 2,000원, L36) | 5단계 |

- 미리 산 몫의 환불: 공개 뒤 7일 안에 다 고르지 않은 포함 사진·보정은 환불된다(D056). 앱은 남은 장수와 기한을 갤러리 위에 보이고, 기한이 지나면 "고르지 않은 n장은 환불됩니다(…)"를 보인다(문구는 정책 세션).
- 신청이 수락되지 않거나(5분 자동 취소) 촬영 시작 전에 취소되면 패키지 결제는 취소·환불 규칙(L26)대로 서버가 처리한다. 앱은 결과만 보인다.
- StoreKit: StoreKit 2(`Product`, `Transaction.updates`)로 산다. 거래는 서버가 검증한 뒤에 고화질본을 연다(B4-3). 같은 사진을 두 번 사지 않게 상품은 소모성(consumable) + 서버의 사진 단위 기록으로 막는다(B4-4).
- 위험
  - **작가별 가격과 IAP 상품**: IAP는 미리 등록한 상품·가격만 팔 수 있다. 추가 사진 가격이 "작가 가격 + 1,000원"(천 원 단위)이므로 가능한 가격마다 상품을 하나씩 등록해야 한다(예: 6,000원·7,000원·… 상한까지). 사진 상한 20,000원(L32)이므로 추가 사진 상품은 6,000~21,000원 16개다. 여기에 보정 7,000원·추가 수정 2,000원 상품이 더해진다. 각 가격이 원화 가격대에 있는지 App Store Connect에서 확인해야 한다(미확인). 서버는 가격 → 상품 ID 표를 갖고, 앱은 그 상품의 스토어 가격을 보인다.
  - 같은 사진이 포함 몫으로도, IAP로도 열릴 수 있으므로 서버가 "이 사진을 무엇으로 받았는지"를 한 곳에 기록해야 한다(이중 결제·이중 차감 방지).
  - 결제 SDK(PG)는 결제창이 앱 밖·웹뷰로 갈 수 있다. 결제 중 앱이 끝나도 서버 결제 상태로 이어 가게 한다(4단계).

## 시험

- 단위 시험(`SBSNCore`): 가격 검증·패키지 총액(D057, Android와 같은 사례), 공개 위치·묶음(칸 경계·같은 칸 유지), 촬영 가능 종료 시각·휴게, 신청 단계(신청·수락·만료·취소)와 촬영 길이·연장 합계, 연락처·링크 탐지(Android와 같은 사례), 갤러리 잠금·편집 기간·삭제 가능, 보정 가격·수정 횟수.

- 교차 조합: 단계마다 iOS ↔ Android 네 조합. 지도 묶음 숫자와 공개 위치가 두 플랫폼에서 같게 보이는지 본다.
