## 0. 공통 원칙

- **MVP 흐름과 공존하지 않고 바꾼다.** 출시 기준 티켓은 새 표시값(예: `deliveryMode = "curatedV2"`, 또는 `flow = "launchV1"`)을 달고, 앱은 지금처럼 모르는 방식의 티켓을 "이전 방식 촬영"으로 안내한다(지금 `isCurated` 처리와 같은 방식). MVP 교차 조합·현장 실증이 끝난 뒤 단계별로 바꾼다.
- **지금 구조를 그대로 쓴다.**
  - 순수 규칙은 `SBSNCore`에 두고 단위 시험한다(예: 공개 위치 계산, 수락 시한, 편집 기간, 연락처 탐지, 촬영 길이).
  - Firestore 접근은 `SBSNBackend`의 `nonisolated static` + `AsyncThrowingStream` 리스너 패턴(`FirestoreListeners`)을 따른다.
  - 두 앱이 같이 쓰는 화면은 `SBSNUI`(지금 `TicketChatView`·`ParticipantsMapView`)에 둔다.
  - 쓰기는 서버 커밋 뒤 화면을 바꾼다(`CustomerTicketView`의 `ticketBeforeWrite` 방식).
  - 시한(5분 수락, 24시간 잠금, 7일)은 **서버 시각 기준**이다. 앱은 표시만 하고, 판정은 규칙·함수가 한다.
- **초 단위 카운트는 쓰지 않는다**(D051). 남은 시간은 분 단위 또는 "14:10까지" 같은 시각으로 보인다.
- **교차 조합**: 상태 이름·문구·시험 식별자(`accessibilityIdentifier`)를 Android와 맞춘다. 단계마다 iOS ↔ Android 네 조합으로 한 사이클을 본다.
- **예시 화면 정리**: 실제 화면이 된 예시(`CustomerFeatures`·`PhotographerFeatures`의 작가 프로필·활동 위치·휴게·수락 설정·바구니·계정 연결·전문 보정 등)는 그 단계에서 예시 목록에서 뺀다(D036 때 P6·P8과 같은 방식).

## 1단계 — 계정과 지도

### 1.1 로그인·계정 연결(두 앱)

- 방향(L04 확정): **고객은 로그인 없이(익명) 지도·프로필을 보고**, 채팅·신청 전에 Google·Apple 로그인한다. 지금 익명 계정에 **연결**(`link`)해 uid를 유지한다. **작가 앱은 처음부터 로그인**한다.
  - 상대에게 보이는 이름은 앱 닉네임이다(L06). 처음 로그인할 때 기본 닉네임을 자동으로 만들고 마이에서 바꾼다. 계정 실명·이메일은 상대·보정사에게 보이지 않는다. 그래서 Apple이 첫 로그인 때만 주는 이름은 화면에 쓰지 않는다(M2, 서버 프로필에 남길지는 웹과 맞춘다).
  - 가입할 때 만 14세 이상 확인 한 줄을 둔다(L28 자리, 문구는 정책 세션).
  - MVP 익명 계정·데이터는 출시 계정으로 옮기지 않는다(L05).
  - 근거: 심사 지침 5.1.1(v) "계정 기능이 핵심이 아니면 로그인 없이 쓰게 하라", 4.8 "Google 로그인을 넣으면 같은 조건의 다른 로그인(Apple 로그인)도 넣어라"(2026-10-16판).
- 화면(공용 `SBSNUI.SignInSheet`)

```
┌──────────────────────────────┐
│  십분스냅에 로그인             │
│  채팅과 촬영 신청은 로그인 뒤   │
│  할 수 있습니다.                │
│                              │
│  [  Apple로 계속하기      ]   │  ← 위에 둔다(같은 크기)
│  [ G  Google로 계속하기   ]   │
│                              │
│  [✓] 만 14세 이상입니다         │  ← L28 자리
│  계속하면 이용약관·개인정보     │
│  처리방침에 동의합니다 ▸        │  ← 동의 방식은 정책 세션 안
│                  [나중에]     │  ← 고객만(둘러보기로 돌아감)
└──────────────────────────────┘
```

- 연결 흐름
  1. 익명 사용자에 Apple·Google 자격 증명을 `link`한다. 성공하면 uid가 같아 티켓·찜·구매·presence가 그대로다.
  2. **이미 다른 계정에 연결된 자격 증명**(`credentialAlreadyInUse` 17025)이면: 그 계정으로 로그인(`signIn`)하고 익명 계정은 버린다. 익명으로는 둘러보기만 하므로(신청·채팅 전 로그인, L04) 옮길 데이터가 없다(B1-2 단순화).
  3. 로그인 계정이 바뀌면(uid 변경) 세션이 리스너·FCM 토큰 등록·로컬 활성 티켓을 새 uid로 다시 시작한다. 지금 `CustomerSession.reissueAccount()`(디버그 "익명 계정 재발급")와 같은 경로를 정식화한다.
- 계정 삭제(마이 → 계정 → 계정 삭제, 두 앱). **삭제를 막지 않는다**(L10).

```
┌──────────────────────────────┐
│ ‹ 계정 삭제                    │
│ 삭제하면 되돌릴 수 없습니다.     │
│ ⚠ 진행 중인 촬영 1건은 취소되고   │  ← 있을 때만. 환불은 취소·환불 규칙대로

│   거래 기록은 법에 따라 분리 보관  │
│ • (작가) 정산할 금액이 있으면     │
│   지급한 뒤 삭제가 끝납니다       │
│ [Apple로 다시 확인하고 삭제]    │  ← 로그인 수단에 맞춰
└──────────────────────────────┘
```

  - Apple 로그인 사용자는 다시 Apple 로그인으로 authorization code를 받아 `Auth.revokeToken(withAuthorizationCode:)` 뒤 삭제한다(Firebase가 Apple 토큰을 저장하지 않음).
  - 서버 데이터 삭제·익명화는 호출형 함수 하나로 한다(B1-3). 앱은 함수 성공 뒤 로그아웃하고 로컬(활성 티켓 ID, 작가 앱 티켓 폴더, 캐시)을 지운다.
- 바뀌는 파일
  - `SBSNBackend/Backend.swift`: `SignIn` actor → 계정 서비스(익명 시작, `link`, `signIn(with:)`, 로그아웃, 삭제, 로그인 상태 스트림). 동시 로그인 한 번만 하는 지금 보호는 유지
  - 새 `SBSNBackend/AccountService.swift`(Apple nonce·Google 자격 증명 만들기, 오류 코드 → 안내 문구)
  - 새 `SBSNUI/SignInSheet.swift`, `SBSNUI/AccountDeletionView.swift`
  - `sbsn/CustomerSession.swift`, `sbsnPhotographer/PhotographerSession.swift`: uid 변경 처리, 로그인 필요 시점 게이트
  - 작가 앱 첫 화면: 로그인 → 역할 문서 확인 → 승인 전이면 "작가 승인 대기" 화면(L07, 촬영 가능 켜기 막음). 같은 계정으로 고객 앱도 쓴다
  - 작가 기기 하나(L08): 다른 기기에서 촬영 가능을 켜면 이 기기는 꺼지고 "다른 기기에서 촬영 가능을 켜 이 기기는 꺼졌습니다"를 보인다(presence의 발행 기기 값으로 판단)
  - 시험 로그인(L09): 디버그 빌드 + sbsn-dev에서만 이메일·비밀번호 시험 계정 화면을 연다
  - `sbsn/ContentView.swift`(로그인 실패 화면), `sbsn/Tabs/CustomerMyTab.swift`·`sbsnPhotographer/Tabs/PhotographerTabs.swift`(계정 섹션, 예시 "계정 연결" 제거)
  - 두 앱 entitlements(Sign in with Apple), Info.plist URL Types(`REVERSED_CLIENT_ID`), `GoogleService-Info.plist` 다시 받기(커밋하지 않음), 패키지 `GoogleSignIn` 10.1.0 이상(Firebase 13과 맞는 판)
- 재사용: 지금 `SignIn` actor의 "진행 중인 로그인 함께 기다리기", 디버그 "익명 계정 재발급"(시험용으로 남김)
- 위험
  - **같은 Apple·Google 계정이면 두 앱의 uid가 같다**(Firebase Auth uid는 프로젝트 단위). 작가가 고객 앱도 쓰면 같은 uid가 `customers/{uid}`와 `photographerPresence/{uid}`를 함께 갖는다. 자기 자신 매칭은 규칙(`customerUid != photographerUid`)이 막는다. 역할은 운영 승인 역할 문서로 정한다(L07, B1-4).
  - 작가 기기는 하나다(L08). 앞 기기의 위치 세션·리스너를 확실히 멈춰야 공개 위치가 두 곳에서 튀지 않는다(B1-5).
  - Apple: 2026-01-01부터 한국 개발자는 Services ID를 새로 등록·수정할 때 서버 간 알림 엔드포인트(이메일 전달 변경·계정 삭제 알림)를 넣어야 한다. Firebase 설정에 Services ID가 필요하므로 엔드포인트가 먼저 있어야 한다(B1-6).
  - 익명 계정 30일 자동 삭제(Identity Platform)를 켜면 둘러보기만 한 사람의 기록이 지워진다. 연결된 계정은 지우지 않는다.
- 백엔드에 필요한 것: B1-1~B1-6("백엔드에 필요한 것" 표)

### 1.2 Google Maps SDK 전환(키·용량·약관·MapKit 대비 위험)

외부 사실은 2026-11-22에 공식 문서로 확인했다(출처는 끝의 "확인한 외부 사실").

- MapKit 대비 위험
  - 지금 쓰는 SwiftUI `Map`(선택 `tag`, `UserAnnotation`, `MapCameraPosition.automatic`)을 모두 직접 구현해야 한다. 접근성(VoiceOver 마커 이름)과 UI 시험 식별자도 래퍼가 맞춰야 한다. 지금 드라이버는 `marker.<이름>` 식별자로 마커를 누른다.

  - Android는 이미 Google Maps라 같은 지도 위에서 교차 조합 화면을 비교하기 쉬워진다.
- 되돌리기: 래퍼 뒤에 지도 구현을 숨기면(입력 = 핀 목록·카메라, 출력 = 선택·보이는 범위) MapKit으로 돌아가기 쉽다.

### 1.3 지도 화면(고객): 화면 범위 작가 표시, 축소 시 숫자 묶음

```
┌──────────────────────────────┐
│ (지도 | 목록)          [필터] │  ← 목록·필터는 지금 예시 자리
│                              │
│      ●김작가          ③       │  ← 200m 칸 안 무작위 점(1분 갱신)
│            ●박작가            │     ③ = 축소했을 때 묶음
│   ☕이작가(휴게 · 점심 13:00까지)│  ← 휴게 중 표시(신청 불가, 채팅 가능)
│        ◉ 나                   │
│                    [⌖ 내 위치] │
│ ┌──────────────────────────┐ │
│ │ 김작가 · 촬영 가능           │ │  ← 핀을 누르면 하단 카드
│ │ 추천 20분 · 평균 2시간 안 전달 │ │
│ │ 10분 9,000원 · 5분당 3,000원  │ │  ← 이 작가가 정한 가격(D057)
│ │ 사진 장당 6,000원             │ │
│ │ [프로필 ▸]   [채팅하기]      │ │
│ └──────────────────────────┘ │
│ Google                        │  ← 로고는 가리지 않는다
└──────────────────────────────┘
```

- 화면 범위 조회: 지도를 움직여 멈추면(`idleAt`) 보이는 범위로 다시 조회한다. 서버가 주는 범위 조회 방식(칸 ID 목록 또는 지오해시 범위, B1-7)에 맞춘다. 한 번에 최대 100명(지금 규칙의 `limit`과 같은 방식).
- 묶음(L30): 두 플랫폼 공통 규칙이다. 200m 격자 칸을 확대 수준에 따라 2배씩 합친 큰 칸으로 모아, 한 칸에 둘 이상이면 숫자 원으로 보인다. 원을 누르면 그 칸으로 확대한다. `SBSNCore` 순수 함수와 Android `:core`가 같은 시험 벡터를 쓴다.
- **공개 위치(L02 확정)**: 작가 앱이 **기기에서** 200m 칸 번호와 칸 안 무작위 점을 계산하고, 서버에는 칸 번호와 표시점만 보낸다. 정밀 좌표는 매칭 전 서버로 가지 않는다(지금 100m 격자도 기기에서 뭉갠다).
  - 무작위 점은 (작가·칸·공개 세션)마다 고정한다. 같은 칸에 있는 동안 1분마다 다시 보내도 점은 같다. 칸을 옮기거나 촬영 가능을 새로 켜면(새 공개 세션) 새 점을 뽑는다.
  - 계산: 공개 세션 비밀값(켤 때 기기에서 만든 난수) + 칸 번호로 결정적 난수를 만들어 칸 안 좌표를 고른다. 비밀값은 서버에 보내지 않는다. 규칙은 `SBSNCore`에 두고 Android와 같은 시험 벡터로 맞춘다.
  - 서버 규칙은 표시점이 그 칸 안에 있는지만 검사할 수 있다(정밀 좌표는 모른다).
- 반경(L11): 반경 밖 고객에게도 핀은 보이되 카드에 "활동 범위 밖"을 보이고 [촬영 신청]을 막는다(채팅은 가능). 반경 값은 300m·500m·1km·2km.
  - **판정 위치가 흐리다**: 서버는 작가 정밀 좌표를 모르고 고객 정밀 위치도 매칭 전에는 서버에 가지 않는다(L13). 그래서 고객 앱이 "내 현재 위치 ↔ 작가 표시점(또는 칸)" 거리로 판정한다. 표시점은 실제 위치에서 최대 약 140m(200m 칸 대각선 절반) 떨어질 수 있어 300m 반경에서는 오차가 크다. 칸 경계까지 거리로 너그럽게 볼지, 서버도 같은 판정을 할지 웹 세션과 맞춘다(B1-10, 열린 질문 N1).
  - 고객이 위치 권한을 주지 않았으면 판정할 수 없다. 이때 "내 위치를 켜면 신청할 수 있습니다"로 막을지 N1에 함께 둔다.
- 휴게·제재(L12): 휴게 중이면 핀에 사유와 끝 시각("휴게 · 점심 13:00까지")을 보이고 신청은 막고 채팅은 열어 둔다. 제재 제한 중인 작가는 지도에서 숨긴다(서버가 조회에서 뺀다).
- 바뀌는 파일
  - `sbsn/Map/PhotographerMapView.swift`: `Map` → `GoogleMapView`, 범위 조회·묶음, 하단 카드(프로필·채팅하기). 지금 "이 작가와 촬영하기"(즉시 확정)는 2단계에서 채팅·신청으로 바뀐다
  - `SBSNBackend/PhotographerDirectory.swift`: 범위 조회 리스너, 공개 위치 필드
  - `SBSNCore/Presence.swift`: `publicGridMeters` 100 → 200, 칸 번호·칸 안 고정 무작위 점(L02), 상태(휴게), 반경·종료 시각, 묶음 함수, 반경 판정

## 2단계 — 매칭·채팅·작가 상태·촬영 길이

### 2.1 고객: 작가 프로필 → 대화 → 촬영 신청

- 흐름: 지도 핀 → 하단 카드 → (프로필) → **채팅하기**(로그인 필요) → 대화방에서 촬영 시간을 정해 **신청** → 작가가 5분 안에 수락하면 매칭 → 위치 공유 시작.
- 작가 프로필

```
┌──────────────────────────────┐
│ ‹ 김작가                       │
│ [사진]  김작가                 │
│        촬영 가능 · 18:00까지    │
│ 추천 촬영 20분 · 평균 2시간 안 전달│  ← 평균은 서버 집계(3단계)
│ 활동 지역: 홍대·연남(반경 2km)   │  ← 홍보용(실제 가능 범위와 별개)
│ 소개: …                        │
│ 기본 10분 9,000원 · 5분당 3,000원 │  ← 작가가 정한 가격(D057)
│ 사진 장당 6,000원                │  ← 미리 사는 가격만(촬영 뒤 가격과 비교하지 않음)
│ 샘플 사진(나중)                 │
│        [채팅하기]               │
└──────────────────────────────┘
```

- 대화방 + 신청(작가별 대화방, 같은 작가와 다시 촬영하면 같은 방)

```
┌──────────────────────────────┐
│ ‹ 김작가 · 촬영 가능   [🗺][…] │  ← 매칭 전에는 위치 단추 없음
│ ─── 11/18 촬영 20분 · 완료 ─── │  ← 지난 티켓 구분선(티켓 단위 내역)
│ …                              │
│ ─── 오늘 ───                    │
│ 고객: 지금 경복궁인데 가능할까요? │
│               작가: 네 가능해요  │
│ ┌──────────────────────────┐ │
│ │ 촬영 시간  [－] 20분 [＋]    │ │  ← 10~60분, 5분 단위(L20)
│ │ 사진       [－]  3장 [＋]    │ │  ← 미리 사는 장수(선택지 미정, D055)
│ │ 전문보정   [－]  1장 [＋]    │ │  ← 미리 사는 보정(선택지 미정, D056)
│ │ 20분 촬영 + 사진 3장 + 보정 1장│ │
│ │ 합계 42,000원 [결제 자리·PG]  │ │  ← 9,000 + 3,000×2 + 6,000×3 + 보정(D057)
│ │ 사진 최소 10장·24시간 안 공개  │ │  ← 약속 문구(L22)
│ │ 철회 불가 한 줄 자리            │ │  ← 상품별 문구는 정책 세션(L27)
│ │        [촬영 신청]           │ │
│ └──────────────────────────┘ │
│ [＋사진][메시지 입력…]  [보내기] │
└──────────────────────────────┘
```

- 신청 뒤(고객)

```
│ ─── 촬영 신청 20분 · 14:10까지 수락 대기 ─── │  ← 시스템 메시지, 초 없이 시각
│ [신청 취소]                                   │
```

  - 작가가 수락하면 "매칭됐습니다 · 위치를 공유합니다"로 바뀌고 위치 단추가 생긴다. 시간이 지나면 "작가가 5분 안에 수락하지 않아 신청이 취소됐습니다"(자동 취소, 서버 판정).
  - 총액(D057): 기본 10분 가격 + 5분 추가당 가격 × (촬영 시간 − 10분) ÷ 5 + 사진 장당 가격 × 장수 + 보정 가격 × 보정 장수. 화면의 계산은 보이기용이고, **서버가 신청 시점의 작가 가격으로 다시 계산해 기록**한다(가격 스냅숏, B4-5). 작가가 신청 뒤 가격을 바꿔도 이 신청에는 영향이 없다. 계산은 `SBSNCore`의 순수 함수(Android와 같은 시험 사례).
  - 패키지(D055·D056): 신청할 때 촬영 시간·미리 사는 사진 장수·미리 사는 보정 장수를 골라 **하나의 가격**으로 PG 결제한다. 촬영 뒤 사진을 고르는 것은 이 계약의 이행이다. 앱은 "미리 사면 더 싸다"는 비교·안내를 하지 않는다. 작가가 수락하지 않아 신청이 취소되면 결제도 취소·환불된다(서버 처리, B4-2).
  - 고객은 한 번에 한 작가에게만 신청한다(L15, 지금 고객 잠금 `customers/{uid}`와 같은 취지). 다른 작가 대화방의 [촬영 신청]은 "진행 중인 신청이 있습니다"로 막는다.
  - 신청을 막는 경우(카드·대화방 막대에 같은 문구): 작가 휴게 중(L12), 활동 범위 밖(L11), 이미 다른 신청·촬영 중. 제재 중인 작가는 지도에서 빠져 있다.
- 바뀌는 파일
  - 새 `sbsn/Chat/ChatRoomView.swift`(고객 대화방·신청 막대), 새 `sbsn/Map/PhotographerProfileView.swift`(예시 `photographerProfile` 대체)
  - `sbsn/Map/PhotographerMapView.swift`: "이 작가와 촬영하기"(즉시 확정 트랜잭션) → 채팅하기
  - `sbsn/Ticket/CustomerTicketView.swift`: 단계에 "신청됨(수락 대기)" 추가. 만남 단계는 대화방이 중심이 되고 지도는 1.4 화면
  - `SBSNBackend/TicketService.swift`: `confirm` → `request(durationMinutes:)`, `withdraw`(신청 취소). 수락·자동 취소는 작가·서버 쪽
  - `SBSNCore/Ticket.swift`: `TicketPhase`에 `requested`, `expired`(자동 취소) 추가, 촬영 길이·연장 필드
- 위험
  - 지금 "고객 확정 = 작가 잠금" 트랜잭션·규칙(D008 레드팀 결과)을 다시 설계한다. 신청 중 작가 잠금 여부, 같은 작가에게 동시에 들어온 여러 신청의 처리(B2-2)가 정해져야 화면이 정해진다.
  - 5분 시한은 서버 시각 판정이다. 작가 폰이 늦게 받은 알림으로 수락을 누를 때 이미 만료된 경우를 안내해야 한다.

### 2.2 작가: 신청 받기·수락·미수락 경고

- 알림: "새 촬영 신청 · 20분 · 14:10까지 수락"(time-sensitive, 지금 매칭 알림과 같은 조합). 알림을 누르면 대화방.
- 홈(촬영 탭)

```
┌──────────────────────────────┐

│ [변경] [휴게] [끄기]           │
│ ⚠ 최근 7일 자동 취소 2회: 한 번  │  ← 경고(제재 초안: 3회째 30분 제한)
│   더 놓치면 30분 동안 새 신청을   │
│   받지 못합니다                 │
│ 새 신청                        │
│ ┌──────────────────────────┐ │
│ │ 고객 A · 20분 · 14:10까지   │ │
│ │ "경복궁 정문 근처예요"       │ │  ← 마지막 메시지
```

### 3.2 고객: 미리보기 전체·개별 저장, 상세 좌우 넘기기, 찜 일괄 구매

- 갤러리

```
┌──────────────────────────────┐
│ ‹ 김작가 · 11/22         […]  │  ← … : 미리보기 전체 저장
│ 사진 13장 · 구매 기한 11/29 14:30│
│ 포함 사진 3장 중 1장 남음 ·      │  ← 미리 산 장수와 기한(D056 자리,
│ 11/29 14:30까지 고르기           │     환불 문구는 정책 세션)
│ 새 사진 1장이 추가됐습니다       │  ← 추가 알림(하루 1번 묶음)
│ ┌──┬──┬──┐                   │
│ │♥ │  │💰│                   │
│ ├──┼──┼──┤                   │
│ │  │♥ │  │                   │
│ └──┴──┴──┘                   │
│ ┌──────────────────────────┐ │
│ │ 찜 3장  [찜한 사진 받기]     │ │  ← 포함 1장 + 추가 2장(IAP)
│ └──────────────────────────┘ │
└──────────────────────────────┘
```

- 상세(좌우 넘기기)

```
┌──────────────────────────────┐
│ ‹ 3 / 13                [⤓]  │  ← ⤓ : 이 미리보기 저장(워터마크)
│                              │
│   ‹    [  미리보기  ]    ›    │  ← 좌우로 넘김
│                              │
│ ♥ 찜     [이 사진 받기(포함)]    │  ← 포함 몫이 없으면 [추가 구매 ₩7,000]
│                                │     (작가 가격+1,000원을 스토어가 준 가격으로, 구매됨이면 "저장됨")
└──────────────────────────────┘
```

  - 미리보기 저장은 워터마크 저화질본이고 메타데이터가 없다(지금 미리보기 그대로, 워터마크 강도 유지 L24). 전체 저장은 갤러리 `…` 메뉴에 둔다(L24). 사진 앱 "추가" 권한을 처음 저장할 때 묻는다(지금 구매 저장과 같은 권한). 워터마크 미리보기는 구매 전 "시험 사용"으로 본다(L27).
  - **사진 받기 순서(D055·D056)**: 미리 산 포함 장수가 남아 있으면 [이 사진 받기(포함)]로 결제 없이 고른다(계약 이행, 확인 한 번). 다 쓰면 단추가 [추가 구매]로 바뀌고 StoreKit IAP로 산다. 서버가 이 티켓의 추가 사진 가격(작가 가격 + 1,000원, D057)에 맞는 상품 ID를 알려 주고, 앱은 그 상품을 조회해 **결제 전에 스토어가 돌려준 실제 가격**(`Product.displayPrice`)을 보인다. 서버 가격과 스토어 가격이 다르면 구매를 막고 알린다(B4-5). 앱 안에 가격 비교·웹 결제 안내는 없다.
  - 포함 장수 표시: "포함 사진 n장 중 m장 남음 · 기한"을 갤러리 위에 둔다. 공개 뒤 7일 안에 다 고르지 않은 몫은 환불된다(D056, 문구는 정책 세션).
  - 미리 산 보정이 있으면 사진을 고를 때 "보정도 맡기기(포함 1장 남음)"를 함께 고른다. 고르면 보정 주문이 들어간다(5단계 흐름).
  - 찜 한꺼번에 받기: 포함 몫부터 채우고 넘는 장수만 IAP로 산다. IAP 거래 단위(장마다 한 거래 / 묶음 상품)는 웹 설계와 맞춘다(B4-4). 일부 실패(기한 지남·삭제됨)는 장별로 알린다.
  - 추가 구매 버튼 옆에 철회 불가 한 줄 자리(L27, 상품별 문구는 정책 세션), 구매 시트 앞에 미성년자 취소권 고지 한 줄 자리(L28). 확인 창은 따로 늘리지 않는다.
  - 작가가 찜한 사진을 지우면 그 칸이 사라지고 "찜한 사진 1장을 작가가 지웠습니다" 안내.
- 바뀌는 파일
  - `sbsn/Photos/TicketPhotoGridView.swift`: 전체 저장 메뉴, 찜 일괄 구매 막대, 추가·삭제 안내. 예시 `basket`·`recommendation` 자리 정리
  - `sbsn/Photos/PhotoDetailView.swift` → 넘기기 상세(`TabView` 페이지 방식, 이웃 미리보기 미리 받기)
  - `sbsn/Photos/PhotoDeliveryManager.swift`: 일괄 구매 순서 처리, 미리보기 저장
  - `sbsn/Gallery/GalleryStore.swift`·`TicketWorkspace.swift`: 공개 목록이 바뀌는 것을 받기(지금은 `galleryPhotoIds` 고정 전제)

## 5단계 — 전문보정 주문(고객)

D051 (8): 기본 사진을 산 고객이 별도 주문, 결과 JPG, 기본본 v1·보정본 v2 따로 보관, 납기 예시 7일, 무료 수정 1회, 추가 수정은 회당 기본 보정료의 20%. 진행은 접수 → 작업 중 → 검수 → 완료, 완료 알림.

- 가격·결제(D055·D056·D057, L25를 대신함): 촬영 신청 때 미리 산 보정은 장당 최소 6,000원(PG, 패키지에 포함), 촬영 뒤 따로 주문하는 보정은 장당 최소 7,000원(StoreKit IAP). 보정 가격을 누가 정하는지(작가·회사·보정사)는 미정이다(N6). 1인·2인 같은 가격. 미리 산 보정은 사진을 고를 때 함께 맡기면 주문된다(3.2). 앱은 두 가격을 비교해 보여 주지 않는다.

## 결제 흐름(D055·D056)

PG 결제창·StoreKit 구매 시트의 세부는 4단계에서 설계한다. 그 전 단계에서는 아래 자리에 지금 `PaymentPlaceholderSheet`("결제 없이 계속")를 두고 기록만 한다. 결제 버튼 옆에는 철회 불가 한 줄(L27, 상품별 문구는 정책 세션), 결제 화면 앞에는 미성년자 취소권 고지 한 줄(L28) 자리를 둔다. 결제마다 확인 창을 늘리지 않는다(L27). 앱 안에 가격 비교 문구와 웹 결제 안내·링크는 넣지 않는다.

| 자리 | 결제 | 가격 | 화면 |
| --- | --- | --- | --- |
| 촬영 신청(패키지) | PG | 작가 가격(D057): 기본 10분(최소 8,000원) + 5분 추가당 × 추가 길이 + 사진 장당(최소 5,000원) × N + 보정(최소 6,000원) × M을 **하나의 가격**으로. 장수 선택지는 미정 | 2.1 신청 막대 |
| 5분 연장 | PG | 작가의 5분 추가당 가격 | 2.5 (작가 동의 뒤) |
| 포함 사진 고르기 | 결제 없음(계약 이행) | — | 3.2 [이 사진 받기(포함)] |
| 추가 사진 | StoreKit IAP | 작가 사진 가격 + 1,000원(서버 계산, 최소 6,000원). 스토어가 준 실제 가격을 표시 | 3.2 [추가 구매] |
| 찜 한꺼번에 받기 | 포함 몫 + 넘는 장수 IAP | 거래 단위는 웹과 맞춤(B4-4) | 3.2 |
| 미리 산 보정 사용 | 결제 없음 | — | 3.2 사진 고를 때 / 5단계 |
| 촬영 뒤 보정 주문 | StoreKit IAP | 최소 7,000원(정하는 주체 미정, N6) | 5단계 |
| 추가 수정 | 미정(N3) | 기본 보정료의 20% | 5단계 |

- 미리 산 몫의 환불: 공개 뒤 7일 안에 다 고르지 않은 포함 사진·보정은 환불된다(D056). 앱은 남은 장수와 기한을 갤러리 위에 보이고, 기한이 지나면 "고르지 않은 n장은 환불됩니다(…)"를 보인다(문구는 정책 세션).
- 신청이 수락되지 않거나(5분 자동 취소) 촬영 시작 전에 취소되면 패키지 결제는 취소·환불 규칙(L26)대로 서버가 처리한다. 앱은 결과만 보인다.
- StoreKit: StoreKit 2(`Product`, `Transaction.updates`)로 산다. 거래는 서버가 검증한 뒤에 고화질본을 연다(B4-3). 같은 사진을 두 번 사지 않게 상품은 소모성(consumable) + 서버의 사진 단위 기록으로 막는다(B4-4).
- 위험
  - **작가별 가격과 IAP 상품**: IAP는 미리 등록한 상품·가격만 팔 수 있다. 추가 사진 가격이 "작가 가격 + 1,000원"(천 원 단위)이므로 가능한 가격마다 상품을 하나씩 등록해야 한다(예: 6,000원·7,000원·… 상한까지). 상한(N5)이 정해져야 상품 수가 정해진다. 각 가격이 원화 가격대에 있는지 App Store Connect에서 확인해야 한다(미확인). 서버는 가격 → 상품 ID 표를 갖고, 앱은 그 상품의 스토어 가격을 보인다.
  - 같은 사진이 포함 몫으로도, IAP로도 열릴 수 있으므로 서버가 "이 사진을 무엇으로 받았는지"를 한 곳에 기록해야 한다(이중 결제·이중 차감 방지).
  - 결제 SDK(PG)는 결제창이 앱 밖·웹뷰로 갈 수 있다. 결제 중 앱이 끝나도 서버 결제 상태로 이어 가게 한다(4단계).

## 시험

- 단위 시험(`SBSNCore`): 가격 검증·패키지 총액(D057, Android와 같은 사례), 공개 위치·묶음(칸 경계·같은 칸 유지), 촬영 가능 종료 시각·휴게, 신청 단계(신청·수락·만료·취소)와 촬영 길이·연장 합계, 연락처·링크 탐지(Android와 같은 사례), 갤러리 잠금·편집 기간·삭제 가능, 보정 가격·수정 횟수.
- UI 시험 드라이버(`CycleDriverUITests`): 로그인은 시험 계정 이름 규칙(작가1·고객1)을 따르되, 실제 Apple·Google 로그인은 자동화하기 어려워 sbsn-dev 전용 시험 로그인 경로(예: 디버그 빌드의 이메일·비밀번호 시험 계정)가 필요하다(B1-9, L09: sbsn-dev에서만). 신청 → 수락 → 시작 → 종료 → 첫 공개(10장 이상) → 구매 순서로 단계를 바꾼다.
- 교차 조합: 단계마다 iOS ↔ Android 네 조합. 지도 묶음 숫자와 공개 위치가 두 플랫폼에서 같게 보이는지 본다.

## 남은 질문(D054 뒤 새로 생김)

- **N1 반경 판정 오차**: 반경 판정에 쓸 작가 위치는 공개 표시점뿐이다(L02로 서버도 정밀 좌표를 모름). 표시점은 실제 위치에서 최대 약 140m 떨어질 수 있어 300m 반경이면 판정이 크게 흔들린다. 제안: "고객 위치 ↔ 작가 칸까지의 가장 가까운 거리"로 너그럽게 판정하고, 고객 위치 권한이 없으면 신청 전에 위치를 켜 달라고 안내한다. 서버도 판정할지는 웹 세션과 맞춘다(B1-10).
- **N2 패키지 결제와 철회 불가 문구 위치**: D055로 패키지는 신청 때 PG로 결제한다. L27은 "촬영 시작" 버튼 옆을 지목했다. 신청 버튼 옆으로 옮길지(결제가 일어나는 곳), 시작 버튼 옆에도 둘지 정책 세션과 맞춘다.
- **N3 추가 수정 결제 수단**: 보정 추가 수정(기본 보정료의 20%)을 IAP 상품으로 둘지 정한다.
- **N4 패키지 선택지**: 미리 사는 사진·보정 장수 선택지(D055·D056에서 미정). 신청 막대의 단계 수가 이것으로 정해진다. 촬영 가격은 작가가 정한다(D057).
- **N5 가격 범위**: 5분 추가당 가격의 최소값, 세 가격(기본 10분·5분당·사진 장당)의 상한. 사진 상한이 IAP 상품 개수를 정한다.
- **N6 보정 가격 주체**: 보정 가격(최소 6,000원·7,000원)을 작가·회사·보정사 중 누가 정하는지. 작가가 정하면 신청 막대·프로필에 보정 가격도 보인다.
